Use a disposable copied world, one dedicated server, and two actual client processes: A is the campaign DM, B an ordinary player. A can also play a bound PC, or control a separately bound NPC. A third client is helpful for unrelated-campaign/private-view checks. ## Install and prepare

1. Build with a complete Java 21 JDK using `./gradlew build runGametest` (cloud helper: `/workspace/cubetable-setup/gradle.sh build runGametest`). Expected checkpoint: **897 assertions and 72 GameTests**. Install `build/libs/tactical-combat-0.1.0.jar` on both clients and server. Use Minecraft 1.21.1, Fabric Loader 0.16.9, Fabric API 0.116.1+1.21.1. Do not install the development GameTest source set. Check the artifact hash against the [checkpoint](phase3-live-checkpoint.md).
2. Preserve backups of the world and existing manual/local sheets. Use a flat, lit stone arena with no lava, water, cliffs or roaming mobs. Stand actors at centered X/Z coordinates ending in `.5`, with feet on solid ground. This is a walking-only controlled encounter; exploration/environment/death rules are not automated D&D.
3. As an operator, A runs `/tbc campaign create SRD acceptance`. The new campaign is selected. Run `/tbc campaign invite B` (replace B with the actual player name), then `/tbc campaign rules srd_5_1`. B selects the campaign through `/sheet` → **Server** → campaign list, or `/tbc campaign select <campaign UUID>`. Operator status is needed for creation, but ordinary authorized campaign DM permissions should subsequently suffice for encounter controls.
4. On B, open **Server** → **New SRD**. Verify draft status, neutral defaults and separation from the local sheet. Use **SRD fields**, then **Validate and stage**, then **Save changes**. Set a clear name, abilities, HP/max/temp, speed, size, armor/proficiencies, weapons and virtual ammunition. Stock is approved character data, not Minecraft inventory. Begin with Medium size, 30 feet, 10 HP and unarmed attacks; use separate higher-HP test drafts for large damage.
5. A reviews the server character and **Approve**s it. Obtain the character UUID and current revision with `/tbc character list` and `/tbc character show <character UUID>`. Bind with `/tbc character bind <character UUID> <revision> B`. B refreshes. Confirm approval, binding, D&D HP/AC/speed and the notice that automatic world combat is disabled. Bound edits must reject even for A.
6. Create/approve/bind A's own SRD character the same way, or create a DM-owned character and bind an explicitly prepared NPC using the existing bind command and an entity selector. NPC creation/spawning/selectors may require ordinary Minecraft operator rights. No vanilla mob stats are automatically converted. Use `/tbc character show` to obtain the bound actor UUID for an NPC. For an easy first run, use the two named players.

## Start, move, attack and end

1. A runs `/tbc srd test-public-ffa A,B` (actual names), or supplies B's name and the bound NPC UUID separated by a comma. The command must reject unauthorized managers, duplicate/unbound/invalid actors, wrong campaign bindings, unsupported clients, zero HP or overlapping encounter ownership without partially recruiting anyone. The acknowledgment supplies the encounter UUID. This explicit mode is **free-for-all: all participants hostile, all locations public even if invisible**.
2. Both clients run `/srdcombat`. If A is a nonparticipating observer, the start command already watches; `/tbc srd watch <encounter UUID>` can reselect the view. Confirm the same active actor/round/order. Each PC sees their own HP/stock; a DM sees campaign actors' private resources. A player must not receive enemy AC, defenses or HP from the public snapshot.
3. If initiative ties, the encounter remains pending. Use **Movement / DM** tie controls to append the tied actors in the proposed order and submit. PC-only ties require matching submissions from every tied PC. Mixed/NPC ties require the DM. Unrelated actors/wrong group/order and unauthorized DM substitution for a PC decision should reject without beginning turns.
4. On the active actor's controller, request the reachable grid. Check the world highlight, local map, selected path, cost and feet remaining. Choose a square and **Move to selected square**. Verify server movement and both clients' positions. Test diagonal five-foot cost, a one-block step, a slab, an obstruction changed after preview, occupied cells, cancellation partway through a route and rapid/delayed requests. Completed squares stay spent. Nonactive actors cannot walk/jump/teleport themselves into a valid attack position. The local map is clipped around the actor; lack of distant-map panning is a known limit.
5. Choose **Attack controls** → weapon, ability, hands, mode and target. Request preview. Check formula, range, damage/type, cover and cost. Preview/cancel must not roll, damage or spend. Confirm once: the server result appears in chat/dice animation, action is spent even on a miss, private HP/temp/stock updates match, and vanilla hearts do not take the SRD damage. Repeated confirmation cannot spend/apply/animate the accepted action twice.
6. Test an invalid target, wall inserted after preview, moved target, stale turn and two rapid controllers attempting the same action. Rejection should name the problem, leave resources intact when not accepted, and require a fresh preview. Repeated grid queries should show a clear rate-limit message after two per second; ordinary request flooding is also bounded.
7. **End turn** advances both clients coherently; DM controls the next bound NPC, or the next PC controls their actor. Complete a round. A runs `/tbc srd end <encounter UUID>` or confirms **End encounter**. Verify ownership, overlays and controls clear; NPC AI returns to its prior state; D&D HP/ammunition is retained rather than reset. Check normal exploration separately in this disposable safe arena.

## Targeting and resource cases

- Repeat with each supported weapon/property configuration: STR/DEX finesse, one-/two-handed versatile, shield conflict, two-handed ranged weapons, proficient/nonproficient armor/weapons and Small/heavy weapons. Invalid choices reject before spending; preview and result agree.
- Test melee at reach and beyond, ranged normal/long/max range, and an adjacent hostile with sight to the attacker. Long range/adjacent hostile impose disadvantage; advantage/disadvantage cancels. Approved arrows/bolts/throwable daggers deplete on accepted misses too; zero stock rejects. Physical arrows/items do not authorize attacks. Crossbow scope is one attack/action, not full Extra Attack/loading automation.
- Build no-cover, low wall, partial-block/corner, three-quarters and full-wall cases. Compare preview to the documented 16-ray adaptation. Intervening creature cover is at most half. Changing cover between preview and confirmation rejects. Camera fading cannot bypass server collision.
- In a **disclosed-position** test only, apply invisibility to attacker, target, then both. Check advantage, disadvantage and cancellation. Total cover still rejects. Do not treat this as testing hidden locations, darkness, hiding or special senses; those are unsupported.
- On separate unbound draft fixtures, approve resistance/vulnerability/immunity and temporary HP, bind, then attack. Verify typed adjustments, temp before current HP and critical dice. Reopen the private character view after ending and restart the server normally to confirm retained resources. Do not modify bound characters to set up cases.
- Reduce D&D HP to zero: the whole encounter must pause; no vanilla death/respawn or death saves should occur. Ordinary move/attack/end-turn rejects. A may run `/tbc srd heal <encounter UUID> <actor UUID> <amount>` while paused, then explicitly end. Healing retains the pause and persists correctly. NPCs use the same pause policy.
- Storage-failure retry is headless fault-tested. If testing a real I/O failure locally, use a disposable copy and restore writable storage before `/tbc srd retry <encounter UUID>`. Expect retained dice, reserved action and no success acknowledgment until commit. Do not improvise a production permission/disk failure. A crash before recovery cannot restore the in-memory encounter/action receipt; manually adjudicate from backups/logs.

## Multiplayer, compatibility and regressions

1. Try an older/no-SRD client in a separate disposable setup: player admission must reject and unsupported controls must not send usable actions. Check client reconnects, server restart and stale encounter packets; no stranded NPC ownership or phantom encounter UI should remain. A disconnect/unload ends this scope's encounter rather than restoring it later.
2. Change the campaign default during an active SRD encounter. Active rules and existing sheets stay SRD. Attempt campaign selection/rebinding while in combat; reject. Run a separate Tactical encounter and another SRD encounter nearby, with actors from distinct campaigns. Verify no recruitment, targeting, damage, private state or turn control crosses boundaries. Repeat after one encounter ends.
3. Verify ordinary B cannot start/end another campaign's encounter, approve themselves, heal/retry as DM, inspect unrelated character data or use forged/stale requests. Test co-DM removal and permission refresh. A participant's own resource readback is allowed; enemy private statistics are not.
4. Repeat character drafting/refresh/conflicts and approval policy checks from Phase 2. Unsaved edits must survive an incoming server revision until explicit reconciliation. New SRD defaults and optional ammo fields must not convert Generic D20/Percentile records or local manual sheets.
5. At 854×480 and common GUI scales (including approximately 427×240 logical size), verify all three SRD pages, confirmation/cancel, tie controls, rejection text, roster pagination, form pagination and the resizable sheet. Test high-DPI/large GUI as well. Check that the selected target highlight and movement overlay are readable and depth-tested. Record clipping/overlap; headless layout reasoning is not acceptance.
6. Test added latency, rapid refresh and duplicate clicks. HP/turn changes should settle on server state, rejected previews must clear safely, animation must not authorize an attack and manual dice remain separate. Use distinct accounts/processes; do not count mock-player tests as this step.
7. Complete the existing Phase 1 Tactical movement, attacks, inventory, projectiles, camera, fading, grid and HUD checks, plus manual dice/card queue and local character-sheet checks. Recheck Tactical vanilla health modifiers and respawn separately; SRD has no vanilla-health modifier integration. Preserve all failures as open gates.

## Acceptance decision

Record results per case with both client logs and the server log. Current decision is **headless gates passed; real-client acceptance Not Verified**. Even a successful checklist permits only the documented controlled SRD scope. It does not enable reactions, death saves, environmental conversion, classes/spells, hidden-information encounters, full monster AI/templates or restart recovery. Resolve grid-query latency and demonstrated client issues before wider deployment. Publishing remains subject to separate authorization.

## Performance branch stabilization acceptance (separate candidate)

The published `dev/phase3-srd-combat` candidate remains fixed at `21e13a4`. The following checks apply to the **local** `dev/phase3-grid-performance` candidate; do not substitute its JAR into the original acceptance record without recording the new commit/hash. Use the final counts in `phase3-performance-checkpoint.md` for this branch. All Phase 1–3 graphical acceptance gates above remain open.

- Compare 30/60/120/300-foot grids in flat, weighted, walled, slab/stair and large-footprint arenas. Above 60 remaining feet, expect a pending response followed by a grid or explicit cancellation. At 4,096 nodes, expect explicit truncation. Record request-to-visible-grid latency separately from server work time.
- Request concurrently from two controllers in separate encounters, then with additional clients. Repeated refresh, cancel, encounter switching and disconnect must release old work; old replies must not replace a newer selection. Original rate limits still apply; a full eight-job queue must reject with retry feedback rather than grow.
- While a large preview is pending, change a block, move an occupant, change turn or revoke campaign permissions. Expect cancellation/denial and require refresh. After completion, obstruct the chosen route: movement must revalidate and reject/stop safely. Recheck unloaded boundaries, world border, diagonal corners and spent movement after interruption.
- Remove a co-DM role without changing the encounter. Their next view must remove private enemy resources. In Tactical, changed HP/turn/action state must update promptly; idle state may use the 20-tick full heartbeat. Reconnect/explicit refresh must restore a full authorized view.
- Keep resolution, GUI scale, camera position, render distance and hardware fixed. Warm the arena, then capture repeated equal-duration Minecraft profiling sessions (F3+L where available) in exploration, Tactical, ordinary SRD and a 4,096-cell SRD preview. Record frame-time distributions and server tick profiles, not just average FPS. Repeat camera/fading, selected-path hovering, dice/card activity and resizable sheets at 854×480 and common GUI scales. Headless map-logic benchmarks do not verify GPU/FPS behavior.
- Run a prolonged disposable multiplayer session with repeated encounters and reconnects. Record heap/GC behavior before and after cleanup. Test larger character stores separately: synchronous durable transactions near the 1,024-record limit remain a known tick-budget risk. Preserve backups; do not disable validation or simulate disk failure in a live world.
